# 📰 OKF 工程：一种新的语义表达范式正在形成

2026 年 6 月 12 日，Google Cloud 没有开发布会，只发了一篇博客和一个 GitHub 仓库，悄悄放出了 v0.1 版的 **Open Knowledge Format（OKF）**——一个开放规范，把知识表示为"带 YAML frontmatter 的 Markdown 文件目录"，目标是让人和 AI Agent 都能读写，无需任何定制工具。

很多人第一眼看到它的反应是：这不就是个文件夹加一堆 Markdown 吗？

是的。但它的意义恰恰在这里。我判断：**OKF 这类"文件化语义"的工程实践，正在成为一种新的语义表达范式**，就像当年的 SQL、后来的 REST API、再后来的 Ontology 一样——它定义的不是一个产品，而是"人、系统、AI 三方共享语义"的最小公约数。

下面从四个角度来进行说明：

---

## 一、大模型的本质特点，决定了语义的载体必须是"文本 + 结构"

先回到原点：大模型到底"吃什么"？

大模型的输入是 token 流，它最擅长处理的是**自然语言 + 轻结构标记**——标题、表格、代码块、列表。这些 Markdown 天然具备的元素，对模型来说就是"语法锚点"，能极大地帮助 Agent 准确提取语义 。

这意味着一个反直觉的结论：

>
>
> 对 AI 最友好的知识形态，不是数据库里的行，不是向量库里的 embedding，而是一份写得好、结构清晰的 Markdown 文档。
>
>

过去两年我们在 RAG 上投入巨大：切片、向量化、召回、重排……本质上都是在做一件事——把"为人写的文档"转换成"机器能用的片段"。这是一条**事后补救**的路径：源头知识是为人类阅读设计的，机器要用，就得先打碎再拼凑，于是有了切片失真、口径不一、上下文过载这些老生常谈的问题。

OKF 的思路是反过来：**从知识的源头就按"人机共读"的格式来组织**。每个概念（Concept）是一个独立的 Markdown 文件，头部带 YAML frontmatter 作为元数据索引卡片——唯一必填字段是 `type`，推荐带上 `title`、`description`、`resource`、`tags`。概念之间用普通的 Markdown 链接互相引用，整个目录自动构成一张关系图。

这不新。`AGENTS.md`、`CLAUDE.md`、Obsidian vault、Karpathy 提出的 "LLM Wiki"，过去一年里无数团队各自把这个模式实现了一遍。OKF 的贡献不是发明，而是**收敛**——给这门已经存在但各说各话的语言，写一部通用语法书。

---

## 二、文档化描述的三个工程红利：可读、可审、可演化

为什么"文档化"这件事本身值得认真对待？因为它同时满足了三类消费者的需求：

## 1. 对人透明，对机器友好。 一个 OKF Bundle 在物理上就是一个普通文件夹：UTF-8 编码的 Markdown + YAML 头信息，不依赖任何云服务或 SDK，可以放本地磁盘、挂容器、打 tar 包、托管 Git 仓库。架构师打开就能读，Agent 读目录就能用。这在历史上很罕见——知识库系统（Confluence、SharePoint）是为人设计的，元数据系统（数据目录）是为数据库设计的，两者对 AI 都天然不友好

## 2. 知识即代码（Knowledge as Code）。 知识一旦落进 Git 仓库，就自动获得了软件工程的全套基础设施：分支、评审、diff、回滚、CI 校验。OKF 的保留文件 log.md 还额外提供了一份审计日志，记录知识包的版本变更历史。对比传统文档协作的混乱生命周期，这是质变。Google 的参考实现甚至给了一个 Enrichment Agent：自动遍历数据集，为每张表生成概念文档，再用第二轮 LLM 调用补充 Schema、引用和关联路径——知识生产本身也开始流水化了

## 3. 生产者与消费者解耦。 OKF 是格式，不是平台。人写的文件可以被 AI 读，元数据导出流水线生成的 Bundle 可以在可视化工具里浏览，一个 LLM 生成的 Bundle 可以被另一个 LLM 查询——格式是契约，两端的工具可以独立替换。规范还要求"容错消费"：消费者必须容忍未知的 type、缺失的可选字段和断裂的链接，一个文件不合规不影响其他文件可用

这三个红利加在一起，意味着语义第一次可以像代码一样被**工程化管理**。

---

## 三、渐进式披露：Agent 读知识的方式，应该是"看地图"而不是"背全书"

这是我认为 OKF 设计里最精妙的一环。

一个 Bundle 的根目录有一个保留文件 `index.md`，它扮演"动态目录"的角色：Agent 检索时先读 index 了解全局结构，再通过标题和一句话描述判断相关性，只精准打开需要的概念文件，然后顺着 Markdown 链接继续深入。

这个机制叫**渐进式披露（Progressive Disclosure）**，它直接回应了大模型应用中最真实的两个痛点：

* **上下文窗口是有限的。** 一次性把几百个文档塞进 prompt，Token 成本爆炸；

* **中间迷失（Lost in the Middle）。** 上下文越长，模型对中段信息的注意力越差，答非所问的概率越高。

同样的思想在 Anthropic 的 Agent Skills 里也能看到：Agent 先发现 Skill 的名字和描述，按需才加载具体指令和资源。这两者的分工其实很清晰：

|        技术        |         回答的问题         |
|:-----------------|:----------------------|
|     **OKF**      | Agent 需要**知道**什么？（知识） |
| **Agent Skills** |Agent 需要**执行**哪些步骤？（规程）|
|**RAG / GraphRAG**|     怎么**找到**相关信息？     |
|     **MCP**      | 能**读写**哪些外部系统、执行哪些动作？ |

知识（Knowledge）与规程（Procedure）分离，检索与调用分离——这套分层一旦成为共识，Agent 系统的架构就从"一坨 prompt + 一堆 tool"进化成了有清晰边界的工程结构。Web 正在长出写给机器的第二层：`llms.txt` 是路标，EntityMap 是人物关系图，OKF 是图书馆本身——它们是堆叠关系，不是替代关系。

## 四、文件关联的理解：从"一堆事实"到"一张图"

单个 Markdown 文件只是事实的容器，OKF 真正的语义价值在**关联**。

概念之间用标准 Markdown 链接互相引用，整个目录自动构成一张关系图。这和传统的知识图谱思路有本质区别：

* **传统知识图谱**：先建模（实体、关系、Schema），再灌数据，语义存在于图数据库的边里，人和 Agent 都得通过查询语言去"取"；

* **OKF 的链接图**：语义就写在文件的链接里，顺着读就能走出来。对 Agent 来说，遍历链接就是推理路径。

如果套用 Agent 记忆的理论框架，OKF 占据的是**语义记忆（Semantic Memory）**的位置——Agent 对你业务世界的稳定认知，独立于任何一次会话：事实、约定、Schema、Join 路径。学术版的做法是向量库加图数据库，工程上真正跑起来的，往往就是一堆 Markdown 文件。而 `log.md` 则顺便承担了**情景记忆（Episodic Memory）**——什么变了、什么时候变的，就躺在它所描述的知识旁边。

这也是为什么我说它和 Ontology 是同构的：Palantir 的 Ontology 用 Object Type、Link Type、Property 把企业语义结构化，OKF 用 Concept、Markdown 链接、frontmatter 做同样的事——只不过后者把载体从"平台内的运行时模型"换成了"任何人都能读写的文件"。一个绑定平台，一个天然可移植。两者不矛盾，反而可以互为镜像。

---

## 五、落地路径：OKF 标准 × 后台工程化 × Agent 理解的三角闭环

规范本身很轻——Google 自己都说，OKF 只定义格式，**不定义运行时**：存储、服务、查询、权限、搜索 API 全都不在规范范围内。所以"用 OKF"不等于"有了系统"，真正的落地是一个三角闭环：

**顶点一：标准化的知识生产（OKF 落地）。**分两条路：核心业务知识（指标口径、业务规则、Runbook）由人手工策展，作为 Source of Truth；海量的技术性元数据（表结构、血缘、API 文档）由流水线自动生成——类似 Google 参考实现里的 Enrichment Agent，从数据源扫描出概念文档，再用 LLM 补充语义描述和关联路径。人工策展保证准确，自动生产保证覆盖。

**顶点二：后台工程化（治理能力）。**文件只是载体，企业级落地需要补齐规范留白的那部分：版本管理（Git 工作流 + `log.md` 审计）、质量校验（link 完整性、type 合法性、口径漂移检测）、权限与合规（IAM 层，决定 Agent 能读什么、不能碰什么）[ ^1^]、定时与事件驱动的更新机制（源系统变更 → 触发概念文档再生成）。这层做好，知识才不会在三个月后变成一屋子过期文件。

**顶点三：Agent 的高效理解（消费闭环）。**Agent 以 `index.md` 为地图做渐进式披露，按需下钻概念文件，沿链接做关联推理；Skills 提供执行规程，MCP 提供对外部系统的读写通道，OKF 提供这两者运行时所依赖的语义底座。理解产生价值，使用中发现的偏差（回答引用了过期口径、某个概念缺失）再回流到生产端，驱动知识更新——闭环形成，知识库开始"自我复利"。

这个三角里，OKF 解决的是**统一语义表达**的问题，工程化解决的是**可持续运营**的问题，Agent 消费验证的是**语义是否真的可用**的问题。三者缺一，都会退化成又一个"建完没人用的知识库"。

---

## 结语

回到标题的判断：为什么说 OKF 工程会成为新的语义表达范式？

因为它踩中了三个历史条件的交汇点：

1. **大模型的母语是文本**，语义表达终于可以用人类自然的方式书写，而不必先翻译成机器专用的结构；

## 2. **Agent 需要可导航的语义图**，而不是每次问答临时拼凑的碎片

1. **工程界已经为"一切皆代码"备好了全部基础设施**，知识是最后一个被纳入的对象。

SQL 统一了"如何向数据库提问"，REST 统一了"系统之间如何对话"，OKF 这类文件化语义规范要做的，是统一**"企业如何向 AI 描述自己"**。

当然，它现在还只是 v0.1，规范粗糙，生态刚起步。但方向已经足够清晰：未来每个数据平台、每个企业级系统，除了给人看的界面和给系统调的 API，还会有第三个交付物——**一份写给 AI 的、可版本化、可导航、可演化的知识包**。

先把这个基础设施建起来的团队，会让自己的 Agent 表现得像一个熟悉业务的老员工，而不是一个什么都要从头问的聪明实习生 。

这就是范式切换的信号
