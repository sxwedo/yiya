# 📰 AI时代，数仓架构和语义层应该怎么搭建

过去几年，很多企业都陆续完成了数据仓库、数据中台和 BI 的建设。但进入 AI 时代以后，一个过去没有那么突出的问题开始变得越来越重要：AI 到底应该怎么理解企业的数据？比如业务人员问 AI：“为什么这个月销售额下降了？”

对于人来说，这句话很好理解。但对于 AI 来说，背后其实是一连串问题：什么叫销售额？按支付算还是按发货算？退款怎么处理？销售额应该从哪张表取？商品、渠道和区域之间是什么关系？同比应该和哪个时间周期比较？当前提问的人又有没有权限看到全国数据？过去，这些知识大量存在于数据开发人员的 SQL、BI 报表、需求文档，甚至人的脑子里。传统 BI 时代，还可以通过“业务提需求—数据开发写 SQL—BI 开发做报表”的方式解决。

但到了 AI 问数、AI 数据诊断和 Vibe Coding BI 时代，这种模式开始遇到明显瓶颈。因为 AI 不仅需要访问数据，更需要理解数据。而这正是语义层重新变得重要的原因。

## 一、语义层是什么？为什么 AI 时代和新 BI 都需要它？

如果用一句话解释：

语义层，就是把底层复杂的数据结构，翻译成业务人员、BI 和 AI 都能够理解的一套统一业务语言。

数据库里可能是 order\_amt、pay\_amt、refund\_amt、sku\_id、channel\_id，但业务真正使用的概念却是销售额、毛利率、复购率、商品、品牌、渠道、区域。所以我更愿意把企业语义层概括成三个核心问题：是什么 → 怎么取 → 谁能看。对应到系统能力，就是三部分：第一，统一指标与业务语义。

解决“是什么”。比如销售额是什么、毛利率怎么算、复购率怎么定义、什么叫新品、什么叫有效会员，以及这些指标能够按照哪些维度分析。这里管理的不只是指标名称，还包括指标口径、计算公式、业务术语、维度、指标关系和指标血缘。第二，面向前端应用的语义数据集。

解决“怎么取”。销售、库存、会员、商品、经营分析等不同主题，可以形成稳定、可复用的数据集。BI、AI Agent 和其他数据应用，不需要理解下面复杂的几十张 DWD、DWS 表，而是基于这些标准数据集进行查询。第三，统一数据权限。解决“谁能看”。比如 CEO 可以看全国数据，区域负责人只能看自己的区域，品牌负责人只能看自己的品牌，一些敏感字段则只有特定角色能够访问。所以如果再进一步浓缩：

语义层 = 统一指标与业务语义 + 面向应用的语义数据集 + 统一数据权限。

为什么到了 AI 时代，这件事情尤其重要？因为传统 BI 本质上还是“人在使用数据”。数据分析师知道应该查哪张表、Join 哪些字段、销售额使用哪个字段、哪些异常数据应该过滤，因此过去企业的数据体系中，其实存在大量“人的隐性知识”。AI 出现以后，这个问题被放大了。假设业务问 AI：“为什么华东区 8 月牙膏销售额同比下降？”

如果没有语义层，AI 首先面对的是几十张甚至几百张表。它需要自己判断哪个字段代表销售额、哪个字段代表华东、商品和品类怎么关联、同比使用哪个时间字段、退款是否扣除。即使 AI 能生成 SQL，也不意味着它生成的是正确的业务 SQL。所以我认为 AI 问数真正困难的地方，从来不只是 Text-to-SQL，而应该是：

Text → Business Semantics → Data → SQL

大模型解决了自然语言理解问题，但企业自己的业务语言，仍然需要企业自己定义。这也是为什么 AI 时代的数据基础设施，需要在“数仓”和“应用”之间增加一层稳定的企业语义层。

## 二、传统数仓和 BI 是怎么实现语义的？为什么现在不够用了？

严格来说，传统数仓并不是没有语义层，只是过去的“语义层”往往没有被独立建设，而是分散在不同地方。典型的传统架构是：业务系统 → ODS → DWD → DWS → ADS → BI其中一部分业务语义存在 DWS，一部分存在 ADS，一部分存在 BI 数据集，还有大量业务口径直接写在 SQL 里面。这就容易产生一个很常见的问题：同样叫“销售额”，财务报表一个口径，运营报表一个口径，电商报表一个口径，老板驾驶舱可能又是一个口径。过去为什么还能运行？

因为中间有“人”。数据开发知道老板驾驶舱应该取哪个销售额，BI 开发知道这个报表应该关联哪张表，业务分析师也知道某些特殊情况应该怎么解释。因此，过去大量的业务语义实际上没有真正沉淀在系统里，而是沉淀在人、SQL、报表和文档里。但 AI 和 Vibe Coding 的出现改变了这件事情。过去可能只有几十个数据开发和 BI 开发人员会写 SQL；未来几百个业务人员都可能通过 AI 自动生成查询、图表甚至分析应用。

这时候，如果底层没有统一语义，AI 能力越强，反而可能让数据口径混乱得越快。比如企业自己都没有统一定义“销售额”，那 AI 又怎么知道哪个销售额才是正确的？所以 AI 时代的数据治理，不能只治理“表”，还必须进一步治理指标、维度、业务术语、数据集以及这些对象之间的关系。这也是传统数仓架构向“数仓 + 独立语义层”演进的根本原因。

## 三、AI时代的新数仓 + 语义层架构应该怎么设计？

基于上面的思路，我设计了一套更适合 AI 和新 BI 的企业数据架构。核心变化是在传统数仓之上增加统一语义层，并在应用侧增加面向业务的指标管理平台，让业务定义、数仓实现以及 BI/AI 消费形成完整闭环。

这套架构整体可以从下往上理解。最下面是数据源层。企业通常已经存在 SAP、OMS、CRM 等成熟业务系统，同时可能已经建设了 MDM 主数据系统。这里需要特别区分 MDM 和数仓的职责。MDM 解决的是“对象是谁”，例如哪个商品、哪个渠道、哪个组织、哪个客户；数仓解决的是“发生了什么”，例如产生了一笔订单、发生了一次支付、产生了一次退款、库存发生了一次变化。

所以 MDM 与数仓并不是替代关系。MDM 为数仓提供统一的商品、渠道、组织等主数据基础，数仓围绕这些统一对象组织企业发生的业务事实。再往上是 DataWorks 数仓层。数仓依然采用比较成熟的 ODS → DWD → DWS 分层。ODS 负责贴源数据，DWD 负责标准化后的业务事实，DWS 围绕销售、库存、会员等公共业务主题形成可复用的数据模型。这里有一个很重要的原则：

有了语义层，并不意味着数仓建模不重要了。恰恰相反，语义层质量的上限，很大程度上取决于下面的数据模型质量。

如果 DWD、DWS 本身就很混乱，业务过程没有划分清楚，商品、渠道、组织等维度没有标准化，那么上面再套一层“语义层”，只是把混乱重新包装了一遍。数仓之上，是整套架构最核心的企业统一语义层。我把它拆成三个核心模块：统一指标管理、面向前端应用的语义数据集、统一权限管控。统一指标管理负责解决“是什么”；语义数据集负责解决“怎么取”；权限体系负责解决“谁能看”。

这样无论上面是传统 BI、Vibe Coding BI，还是 Data Agent，面对的都是同一套业务语言和数据口径。再往上是应用层。这里除了 Vibe Coding BI 和 Data Agent，我增加了一个很重要的模块——面向业务侧的指标管理平台。这个平台不是给数据开发人员使用的，而是让业务真正参与指标治理。业务人员可以在这里查看指标、搜索指标、维护业务口径、讨论指标定义、提交指标需求和发起指标变更。

这样整个架构实际上形成了一个比较清晰的职责分工：MDM 管对象，数仓管事实，语义层管业务含义，指标平台让业务参与定义，BI 和 AI 负责消费数据。我认为这比传统“业务提需求—数仓做表—BI 做报表”的模式更适合 AI 时代。

## 四、怎么真正搭建这套语义层？

架构图比较容易画，真正困难的是怎么把它落地。我认为可以按照 “业务指标 → 指标工程化 → 数仓模型 → 语义数据集 → BI/AI 应用” 这条链路逐步建设，而不是一开始就在 DataWorks 里面设计几百个所谓的“标准指标”。

第一步：从业务真正使用的指标开始

首先盘点企业目前真正使用的指标，比如销售额、销售数量、毛利额、毛利率、库存周转、复购率、会员数、新品销售占比等。然后让业务确认这些指标真正的业务定义：统计范围是什么？时间口径是什么？退款怎么算？哪些订单状态参与统计？适用于哪些组织和渠道？这里最重要的是：业务负责确认“这个数字代表什么”，而不是让业务去设计底层 SQL。

第二步：把业务指标工程化

业务确认“销售额是什么”以后，数据团队再解决“销售额怎么实现”。这时候可以把业务指标进一步工程化拆解成原子指标、修饰词、时间周期、派生指标、复合指标，并进一步关联事实表、维度和具体计算逻辑。例如业务定义一个“天猫近 30 天销售额”，底层可以拆成：支付金额（原子指标） + 天猫（修饰条件） + 近30天（时间周期） → 天猫近30天销售额（派生指标）毛利率则可以继续由毛利额和销售额等指标组合得到。

这样做最大的价值，是企业几百个业务指标背后，不再是几百段彼此独立的 SQL，而是建立在一套可复用的指标积木之上。这里我建议坚持一个原则：

业务指标平台负责 What，DataWorks 负责 How。

业务指标平台维护业务定义和业务 Owner，DataWorks 负责把它工程化成真正可执行的数据模型和计算逻辑。业务平台中的指标定义可以通过接口同步到 DataWorks，但不建议业务修改指标以后直接改变生产数仓逻辑。更合理的是经过业务确认 → 数据评估 → 开发测试 → 发布生效的过程，并通过 Metric ID、Version 和指标血缘建立业务定义与技术实现之间的映射。

这样既避免业务直接操作复杂的数仓系统，又避免业务指标平台和 DataWorks 最后演变成两套互相冲突的指标库。

第三步：建设面向应用的语义数据集

只有指标还不够，因为 BI 和 AI 最终还是需要查询数据。因此需要进一步把指标 + 维度 + 业务关系组织成面向应用的数据集，例如销售分析数据集、商品分析数据集、库存分析数据集、会员分析数据集、经营分析数据集。这里尤其要避免重新回到传统 ADS 的老路：一个报表建一张表，一个需求再建一张表。语义数据集应该围绕相对稳定的业务主题设计，而不是围绕某一张 BI 页面设计。页面会不断变化，但销售、商品、会员、库存这些核心业务主题相对稳定。

第四步：把权限真正纳入语义层

语义层除了指标和数据集，还必须管理权限。例如华东区域负责人可以查询销售额，但只能查询 region = 华东；品牌负责人只能查询自己负责的品牌；手机号、身份证等敏感字段则需要进一步限制。这里要特别注意：语义权限不等于物理权限。语义层负责定义“这个角色能够看到什么”，最终还需要和 DataWorks、底层计算引擎以及数据服务/API 的实际权限打通。最终应该形成：业务组织/角色 → 语义权限策略 → 数据服务/查询引擎 → 底层数据权限

这样权限才真正形成闭环。

第五步：让 Vibe Coding BI 和 Data Agent 统一从语义层消费数据

这一点可能是整个架构能否成功的关键。Vibe Coding BI 不应该自由理解下面复杂的 DWD/DWS 表，而应该优先通过统一语义层获取指标、维度、数据集和权限信息。未来业务人员可能只需要说：“帮我做一个今年各渠道销售趋势分析。”Vibe Coding BI 根据自然语言理解业务意图，从语义层找到“销售额”指标、渠道维度、时间维度和对应数据集，在权限允许的范围内生成查询，然后生成图表和分析应用。Data Agent 同样如此。例如业务问：

“为什么 8 月销售额同比下降？”Agent 首先通过语义层知道什么是销售额、同比是什么意思、有哪些可分析维度、当前用户能够访问哪些数据，然后再进行渠道、商品、区域、价格、销量等维度的逐层拆解。因此未来真正有价值的企业 Data Agent，并不只是：LLM + SQL而更接近：

LLM + 企业语义层 + 数据模型 + 分析能力

LLM 提供通用智能，而语义层提供的是企业自己的“业务常识”。这也是为什么我认为未来正式经营分析应该尽量遵守一个原则：BI 和 AI 使用同一个语义层，而不是 BI 一套口径、AI 又重新理解一套口径。

## 五、结语：AI 时代，最稀缺的可能不是数据，而是“被定义好的数据”

过去二十年，企业已经积累了大量数据。所以今天真正的问题越来越不是：“有没有数据？”而是：“这些数据到底是什么意思？”如果销售额有五个定义，商品没有统一编码，渠道没有统一分类，同一个指标在不同 BI 里面存在不同 SQL，那么再强的 AI，也只能在混乱的数据基础上更快速地制造混乱。AI 可以极大降低数据应用的开发门槛，但它不会自动解决企业的数据治理问题。甚至恰恰相反：AI 会把企业过去隐藏的数据治理问题进一步放大。

过去只有数据开发人员可以写 SQL，口径问题影响的是几十个人；未来几百个业务人员都可以通过 AI 自动生成查询和分析应用，数据语义一旦没有治理好，问题反而会被快速放大。因此，AI 时代企业真正需要重新建设的，不一定只是一个更大的数据仓库，而是一套能够让人和 AI 共同理解企业数据的基础设施。从这个角度重新看整个架构：

MDM 是主数据中心，解决“对象是谁”；DataWorks 数仓是事实数据中心，解决“发生了什么”；指标平台 + 统一语义层是业务语义中心，解决“是什么意思、怎么算、怎么取、谁能看”；Vibe Coding BI + Data Agent 是数据消费层，解决“如何把数据变成分析、洞察和决策”。最终，我认为这套架构真正需要守住的是三个“一”：

业务定义只有一个源头。技术实现只有一个源头。BI 和 AI 只有一个正式的语义取数入口。

当这三件事情真正建立起来以后，企业的数据体系才有可能从过去的“人找数据”，逐渐走向“AI 理解数据，并帮助人做决策”。而这，可能才是 AI 时代重新建设数仓和语义层最大的价值。
