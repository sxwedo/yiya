# 📰 什么是 Eval？为什么它决定了 AI 项目能不能真正落地

现在很多人都会做 Agent。

Prompt、RAG、Workflow、Knowledge Base、MCP、Tool Calling……

一个 Demo 很快就能跑起来。

然后大家会说：

“效果不错。”

但我越来越觉得，这句话其实很危险。

因为，什么叫不错？

100 个问题，答对多少？

哪种问题最容易答错？

Prompt 修改以后真的提升了吗？

知识库换了以后，幻觉减少了吗？

V2 到底比 V1 好在哪里？

如果没有一套固定的问题、一套明确的评分标准，以及一份可以对比的报告，你其实不知道答案。

你只有一种感觉：它好像变聪明了。

> 没有 Eval，你根本不知道 AI 是真的变好了，还是只是“感觉变好了”。

# 1\. Eval 到底是什么？

Eval 是 Evaluation 的缩写，中文就是“评估”。

但如果只把它解释成“评估模型效果”，大多数人看完还是不知道该做什么。

我更喜欢一个简单的比喻：

> Eval，就是给 AI 考试。

学校不会因为一个学生“看起来挺聪明”，就说他数学学得很好。

至少还需要一套考试制度：

- 考试题

- 标准答案

- 评分标准

- 阅卷方式

- 成绩单

- 错题分析

- 下一轮复习

AI 也是一样。

学校里的考试AI 项目里的对应物考试题库Golden Set：一组经过验证的代表性案例标准答案参考答案、事实依据或必须满足的条件评分标准Rubric：把“好不好”拆成可检查的维度阅卷规则、LLM-as-a-Judge，或人工复核成绩单Eval Report：版本、指标与失败样本错题本Error Analysis：失败类型与根因继续学习Prompt、RAG、Workflow、模型与工具的迭代

所以，Eval 不只是跑一次 benchmark，也不只是给模型一个总分。

它更像一条闭环：

准备题目 → 运行系统 → 按标准评分 → 读懂失败 → 修改系统 → 再考一次。

真正有价值的 Eval，不是告诉你“这个模型有多强”，而是告诉你：

你的这个 AI 产品，在你的真实任务上，究竟哪里有效，哪里不可靠。

# 2\. 为什么 AI 比传统软件更需要 Eval？

传统软件的测试，通常有很清楚的输入和输出。

输入 1 + 1，正确结果是 2。

输入一个订单，系统应该返回一个确定的金额。

只要实际输出和预期输出不一致，测试就失败。

这类系统往往接近 deterministic：

同一个输入，在相同条件下应该得到同一个结果。

AI 不一样。

比如让 AI 写一封“礼貌但有力度的催款邮件”。

这里可能存在几十种合格答案。

它们的句子不同、结构不同、措辞不同，但都可能满足要求。

这时你不能简单写：

actual\_output == expected\_output

你要问的是：

- 有没有解决用户的问题？

- 事实是否准确？

- 有没有编造不存在的信息？

- 是否遵循了语气和格式要求？

- 是否遗漏了关键条件？

- 是否违反了业务规则？

> Testing 更多在回答：它能不能跑？Eval 更多在回答：它跑得好不好？

Testing 当然仍然重要。

API 能不能调用、JSON 能不能解析、工具参数是否正确，这些都应该用传统测试尽快挡住。

但“调用成功”不等于“任务完成”。

一个 Agent 可以每次都返回合法 JSON，却每次都把客户分错类；

可以成功调用搜索工具，却把搜索结果理解错；

可以流畅地回答问题，却在关键事实上产生幻觉。

Testing 保证系统没有坏掉。

Eval 帮你判断系统有没有变得更有用。

# 3\. 没有 Eval 的 AI 项目有多危险？

最常见的 AI 开发流程是这样的：

V1 做出来了。大家体验以后觉得不错。

于是改 Prompt。

V2 出来了。大家又觉得更聪明了。

然后换模型、换知识库、加一个工具、调整上下文长度。

V3 看起来更快了。

整个过程里，却没有人能回答：

- V2 比 V1 到底提升了多少？

- 是所有任务都提升，还是只改善了某一类问题？

- 哪些任务反而退化了？

- 幻觉率有没有变化？

- 成本和延迟有没有恶化？

- 新增的工具到底带来了价值，还是只是让系统更复杂？

最后，项目变成了“凭感觉调 Prompt”。

这不是因为团队不认真，而是因为 AI 的输出太容易让人产生错觉。

一个更长、更自信、更像人写的答案，很容易被误认为是一个更好的答案。

> 没有 Eval 的 AI 开发，本质上很容易变成“凭感觉调 Prompt”。

软件工程靠 Test 防止代码回归。

AI 工程需要 Eval 防止能力回归。

# 4\. Golden Set：AI 的考试题库

Golden Set 可以先理解为：

> 一组经过人工验证的高质量标准案例。

它不是随便收集的几十个问题，也不是从网上抄来的 benchmark。

它应该尽量贴近你的产品会遇到的真实任务，并且已经有人认真确认过“什么算对”。

举个 AI 招聘 Agent 的例子。

假设系统要根据简历和岗位描述给候选人打分，并决定是否进入面试。

如果 AI 对“简历 01”给出 82 分，我们首先要问的不是这个数字看起来是否合理，而是：

这个判断和有经验的 HR 是否一致？

因此，HR 可以先建立一份标准案例：

案例人工标准关键理由简历 01应通过核心经验与岗位要求高度匹配简历 02应淘汰缺少必须技能，且经历无法替代简历 0375–85 分有相关经验，但管理范围不足简历 04不超过 60 分项目名称相似，实际职责不匹配

然后让 AI 批量测试，再观察它和人工标准之间差多少。

这样，Golden Set 就把“这个 AI 看起来会招聘”变成了一个可以检查的问题：

在这组代表性案例上，它的判断是否稳定、是否接近业务标准、错误集中在哪里？

一份有用的 Golden Set，至少应该包含：

- 高频场景

- 边界场景

- 异常场景

- 容易混淆的场景

- 高风险场景

- 历史失败案例

题库不一定一开始就很大。

20 个高质量、覆盖关键风险的案例，往往比 200 个重复问题更有价值。

> 最有价值的 Eval 数据，往往不是成功案例，而是 AI 曾经真正犯过的错。

# 5\. Rubric：AI 的阅卷标准

题库有了，还不够。

因为很多 AI 任务没有唯一标准答案。

你还需要告诉阅卷者：

什么是好的答案，什么是勉强合格，什么是不可接受。

这就是 Rubric。

比如评估一篇 AI 生成的行业文章，可以把 100 分拆成：

维度权重检查什么事实准确性30关键事实、数字、因果关系是否可靠是否解决问题25是否直接回应了用户真正的任务引用正确性20引用是否存在、是否真的支持结论品牌信息10产品名、功能和边界是否表达正确合规性10是否出现不该承诺或不该输出的内容格式5标题、长度、结构是否符合要求

于是，“我觉得挺好”就可以被拆成一组更具体的判断：

事实准确 28/30，问题解决 21/25，引用正确 16/20，品牌信息 9/10，合规 10/10，格式 5/5，总分 89。

这并不意味着分数从此变成绝对客观。

Rubric 仍然需要人来设计、校准和更新。

但它至少把讨论从模糊的偏好，推进到了可以复盘的维度。

> Rubric 的本质，是把模糊的主观判断结构化。

写 Rubric 时，一个常见误区是只写“要高质量”。

这几乎无法执行。

更好的写法是写成可观察的标准：

- 5 分：所有关键事实都能被给定资料支持，没有重大错误

- 3 分：主结论基本正确，但遗漏一项重要限定条件

- 1 分：出现一个会改变决策的事实错误

当评分标准能让两个不同的人给出相近的分数时，Rubric 才真正开始工作。

# 6\. 谁来给 AI 打分？

通常有三种阅卷方式。

## 规则评分

规则最适合判断那些明确、机械、无需理解语义的条件：

- JSON 是否能被解析

- 必须字段是否存在

- 字段类型是否正确

- 是否包含 URL

- 是否超过长度限制

- 是否出现禁用词

- 数字、日期和格式是否符合业务要求

规则评分便宜、稳定、可解释。

能用规则判断的地方，不必强行交给模型。

## 人工评分

人工适合高风险、复杂、需要领域经验的任务，例如：

医疗、法律、招聘、金融建议和品牌内容。

人工评分成本更高，也可能不一致，但它能帮助团队发现原本没有想到的错误类型，并用来校准自动评分器。

## LLM-as-a-Judge

LLM-as-a-Judge，就是让另一个模型按照 Rubric 给目标 AI 的答案评分。

一个简化的 Judge 指令可能是：

请按照以下标准评估候选答案。

准确性：0–5 分
完整性：0–5 分
相关性：0–5 分
逻辑性：0–5 分

请输出：
总分、每项理由、最严重的问题、是否建议通过。

它的优势是速度快、规模大，特别适合初筛、回归测试和发现趋势。

但它不是绝对真理。

LLM Judge 也可能：

- 受措辞影响

- 偏好更长的答案

- 对自己熟悉的模型更宽容

- 在相同输入下给出不稳定分数

- 被格式设计诱导出高分

因此，真实项目更适合采用组合方式：

![Image](../_media/x-2093183040952623415/UPing123zzz_2093183040952623415_2.jpg)

规则先挡住硬错误，LLM Judge 处理大规模语义判断，人工复核高风险和争议样本。  

7\. Eval Report：真正的 AI 成绩单

如果没有报告，Eval 很容易停留在“跑过了”。

Eval Report 的作用，是把一次考试变成可以比较的证据。

指标V1V2变化总体通过率71%91%+20 个百分点事实准确率85%96%+11 个百分点格式正确率92%99%+7 个百分点幻觉率14%4%−10 个百分点平均响应时间8.2s5.4s−34%单次成本¥0.18¥0.11−39%

这时候，才可以比较有把握地说：

V2 比 V1 更好。

准确率提高了，幻觉下降了，响应速度提高了，成本还降低了。

真实项目还要看不同切片：

- 新用户和老用户

- 中文和英文

- 简单问题和复杂问题

- 不同客户行业

- 不同风险等级

总体平均分可能上涨，但某个关键客户的高风险任务可能退化。

一个合格的报告，不应该用平均数把这种问题遮掉。

# 8\. 真正正确的 AI 开发流程

![Image](../_media/x-2093183040952623415/UPing123zzz_2093183040952623415_4.jpg)

传统项目经常把开发流程想成：

Build → Done

但 AI 产品更像这样：

Build → Eval → Analyze → Improve → Eval Again

每一轮迭代都应该留下可追踪的东西：

- 这次改了什么？

- 哪些题目变好了？

- 哪些题目退化了？

- 新增的通过率来自哪里？

- 成本、延迟和稳定性付出了什么代价？

- 还剩哪些失败类型？

比如一个客服 Agent 在订单查询上表现不好。

你跑完 Eval 发现，问题不是模型不会回答，而是订单工具在缺少订单号时被错误调用；工具返回空结果后，模型又把“查不到”编成了一个具体状态。

如果只盯着最终答案，你可能会继续改 Prompt。

如果有失败样本和链路记录，你会看到更准确的根因：

参数提取、工具调用条件和空结果处理都需要修正。

这就是 Eval Engineering 和“测一下效果”的差别。

它要求你把评估本身也当作工程系统来建设：

数据集可版本化，运行可复现，指标可比较，失败可追踪，评分器可校准。 

9\. 为什么 Eval 是 AI FDE 的核心能力之一？

以前我觉得 AI 工程师最重要的是：

Prompt、RAG、Agent、Workflow、MCP、Tool Calling。

后来越来越发现，这些能力主要解决的是：

> 怎么把东西做出来。

而 Eval 解决的是：

> 怎么证明你做出来的东西真的有效。

对个人 Demo 来说，“我试了几个问题，感觉不错”也许够用。

但在真实交付里，企业买的不是一个 Agent 的概念，而是一个结果。

客户会问：

- 准确率是多少？

- 在哪些场景下稳定？

- 为什么可以相信它？

- 出错时谁能发现？

- 新版本提升了多少？

- 成本是否在可接受范围内？

- 能不能安全地进入生产？

如果这些问题回答不了，技术再炫酷，也很难真正获得信任。

FDE 的价值，往往就在“把技术能力翻译成客户结果”。

而 Eval 提供了这套翻译所需要的证据：

基线、指标、失败案例、改进前后对比，以及上线后的持续监控。

> Demo 展示能力，Eval 建立信任。

# 10\. 做任何 AI 项目，我以后都会先问这 6 个问题

1. 我怎么证明它真的有效？

1. 我的 Golden Set 是什么？

1. 我的评分标准是什么？

1. 当前成功率是多少？

1. 最常见的失败类型是什么？

1. 新版本相比旧版本提升了多少？

如果这六个问题回答不了，那这个 AI 系统可能还没有真正完成。

它也许已经能运行，甚至已经能演示。

但“能运行”和“可交付”之间，通常还隔着一套 Eval。

# 结语：从会做 Demo，到能证明结果

过去，AI 开发的门槛是“能不能做出来”。

现在模型越来越强，做一个 Demo 正在快速变简单。

未来真正拉开差距的，可能不再是谁最会写 Prompt，而是谁能够：

- 定义问题

- 建立题库

- 设计评价标准

- 找到失败案例

- 持续迭代系统

- 最终用数据证明这个 AI 真的有效

把这件事说得更简单一点：

> Eval = 给 AI 考试。Golden Set = 考试题库。Rubric = 阅卷标准。Eval Report = 成绩单。Eval Engineering = 建立整套 AI 考试制度。

没有 Eval，你只能说 AI“看起来不错”；有了 Eval，你才能证明它真的不错。
