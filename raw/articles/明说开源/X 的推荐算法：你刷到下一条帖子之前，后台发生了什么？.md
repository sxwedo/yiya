# 📰 X 的推荐算法：你刷到下一条帖子之前，后台发生了什么？

就在今天，马斯克转发了X开源团队最新的动态。

没错，X的推荐算法又定期开源了。

https://github.com/xai-org/x-algorithm

你打开 X。

手指往上一划。

一条帖子出现了。

看起来只是一个很自然的动作，后台其实已经完成了几轮判断：

- 这条帖子为什么有资格进入候选？

- 你可能会对它做什么？

- 它会让你停留，还是让你马上划走？

- 它虽然可能有吸引力，但会不会带来举报、拉黑或负反馈？

- 你刚刚已经看过三个相同作者了，还要不要继续推？

- 这条内容即使得分很高，是否仍然因为规则原因不能展示？

这套系统的核心，可以先浓缩成一句话：

> X 试图预测的，不只是“你会不会点开”，还包括“你看完之后会做什么”。

这次开源的 commit，重点就在于：把这套预测、排序、过滤和部署流程进一步整理成了一套更完整的生产系统。

---

# 先看一条帖子是怎么被选中的

假设系统现在有两条帖子。

## A：一篇扎实的技术分析

作者是你关注的人，过去你读过他的几篇文章。

系统可能观察到：

\`\`\`plaintext
你读完的概率：高
点赞概率：中高
回复概率：中
停留时间：长
负反馈概率：低
\`\`\`

## B：一条很刺激的观点

作者你没关注，标题非常抓眼球。

系统可能判断：

\`\`\`
点开概率：高
停留时间：中低
转发概率：中高
负反馈概率：高
举报概率：中
\`\`\`

如果只看点击，B 很可能赢。

但 X 的排序系统会把这些行为拆开预测，再综合起来计算：

\`\`\`
点赞
回复
转发
引用
停留
关注作者
点击链接
快速划走
标记不感兴趣
举报
拉黑

\`\`\`

于是，最终问题变成：

\`\`\`
这条帖子能带来多少正向互动？
会带来多少阅读价值？
产生负反馈的风险有多大？
\`\`\`

这就比一个简单的“点击率”复杂得多。

---

# 第一关：全站内容太多，先找候选

X 不可能让复杂模型检查全站每一条帖子。

如果全站有几亿条内容，逐条计算会非常昂贵。

所以系统第一步做的是召回。

它会从不同地方找内容：

- 你关注的作者；

- 你最近互动过的作者；

- 和你近期阅读内容相似的帖子；

- 兴趣相近的人喜欢的内容；

- 热门帖子；

- 你没有关注、但系统认为可能相关的作者；

- 与当前话题、搜索词或实时事件相关的内容。

这一关的任务很像图书馆管理员：

\`\`\`
整个图书馆有 100 万本书
先找出 1000 本可能适合你看的
\`\`\`

召回阶段不追求最终排序。

它只需要尽量保证：

> 真正有价值的内容不要太早被漏掉。

所以这里会有多个召回通道并行工作。

每个通道的来源不同：

\`\`\`
关注关系召回
相似内容召回
社交关系召回
热门内容召回
实时话题召回
\`\`\`

它们合起来，得到一批候选帖子。

---

# 第二关：系统开始观察“现在的你”

推荐系统不能只依赖一份固定用户档案。

你以前喜欢编程，不代表你今天还只想看编程。

也许今天上午你连续看了十条人工智能创业内容，下午开始关注某个体育比赛，晚上又回到技术讨论。

所以系统会看你的近期行为序列：

\`\`\`
你刚刚看过什么？
在哪条帖子上停留很久？
有没有点赞？
有没有回复？
有没有点开作者主页？
有没有连续阅读同一个话题？
哪些内容被你快速划走？
\`\`\`

这里有一个关键变化：

\`\`\`
用户画像 ≈ 一张静态标签表
\`\`\`

逐渐变成：

\`\`\`
用户画像 ≈ 一段不断变化的行为轨迹
\`\`\`

系统更关心：

> 你最近正在对什么产生兴趣？

这也是为什么你刚刚连续看了几条某个主题的内容，信息流往往很快就会继续推送类似内容。

---

# 第三关：Phoenix 给每条帖子做“行为预测”

现在，候选帖子已经准备好了。

Phoenix 模型开始逐条分析。

它会把用户最近的行为、帖子内容、作者信息以及其他上下文放到一起，预测用户可能做出的反应。

可以把模型输出想象（注意我这里的用词）成这样：

\`\`\`
帖子 A：
点赞概率       0.30
回复概率       0.12
转发概率       0.08
长时间停留概率 0.60
关注作者概率   0.04
负反馈概率     0.03
举报概率       0.01
\`\`\`

注意，这里有很多个输出。

这类设计通常叫多任务学习或多动作预测。

模型同时学习多个任务：

\`\`\`
任务 1：预测点赞
任务 2：预测回复
任务 3：预测转发
任务 4：预测停留
任务 5：预测负反馈
任务 6：预测举报
\`\`\`

每个任务都可以有自己的预测头。

简化成结构，大概像这样：

\`\`\`
用户历史 ─────┐
├──→ 共享神经网络 ──→ 点赞预测
帖子信息 ─────┤                  ├──→ 回复预测
│                  ├──→ 转发预测
作者信息 ─────┘                  ├──→ 停留预测
├──→ 负反馈预测
└──→ 举报预测
\`\`\`

前面的网络共享信息，后面针对不同动作分别输出结果。

为什么要这样做？

因为用户行为本身就有很多种。

一条帖子可能：

- 很容易被点击，但读完就走；

- 不容易被点赞，却能让用户认真阅读；

- 引发大量回复，但回复内容主要是争吵；

- 被大量转发，同时也带来很多举报。

如果所有事情都压缩成一个“喜欢分”，很多差异就会消失。

多任务模型相当于给帖子建立了一张更详细的行为预测表。

---

# 第四关：RankingScorer 把多项预测合成一个排名

Phoenix 输出的是一组概率。

信息流最终需要一个排序依据。

这时候由 \`RankingScorer\` 把多个预测组合起来。

一个简化版本可以写成：

\`\`\`
综合分数 =
点赞概率 × 点赞权重
\+ 回复概率 × 回复权重
\+ 转发概率 × 转发权重
\+ 停留概率 × 停留权重
\+ 关注概率 × 关注权重
\- 负反馈概率 × 惩罚权重
\- 举报概率 × 惩罚权重
\`\`\`

这不是公开代码中的完整公式，只是帮助理解结构的简化表达。

真正重要的地方在于：

> 模型负责预测各种行为，排序器负责决定这些行为在当前产品目标下值多少钱。

比如：

- 点赞权重高，信息流会更偏向容易获得点赞的内容；

- 回复权重高，信息流可能更偏向容易引发讨论的内容；

- 停留权重高，长内容或连续阅读内容可能更占优势；

- 负反馈惩罚高，争议性或刺激性内容会更谨慎；

- 新作者加成高，陌生作者有更多机会进入信息流。

所以，推荐系统的结果不只取决于模型。

同一个模型，换一组权重，最后的内容风格就可能变化。

---

# 一个容易被忽视的问题：互动越多，内容就越好吗？

不一定。

一条帖子有很多回复，可能代表：

- 大家很感兴趣；

- 观点很有争议；

- 评论区正在争吵；

- 用户围绕它展开了高质量讨论。

这几种情况，在“回复数量”上可能很像，在用户体验上却完全不同。

同样：

停留时间长

可能是因为用户认真阅读，也可能是因为内容太难，或者用户正在反复确认自己有没有看懂。

因此，多动作预测能让系统看到更多信号，但它没有自动解决“如何理解行为”的问题。

这也是推荐系统最难的地方之一：

> 行为容易记录，行为背后的原因很难判断。

# 第五关：高分帖子也不一定能展示

排序解决的是：

> 哪些内容更值得排在前面？

Visibility Filtering 解决的是：

> 这条内容是否允许出现？

一条帖子即使预测互动很高，也可能被过滤掉。

原因可能包括：

- 账号受到限制；

- 内容违反平台规则；

- 被识别为垃圾信息；

- 正在审核；

- 不符合某些地区或年龄要求；

- 存在安全风险。

所以系统里有两套不同的判断：

\`\`\`
排序：
在合格内容里，谁排前面？
可见性：
谁有资格进入结果？
\`\`\`

可以把它理解成考试和入场券。

排序像是在考场里排名。

可见性过滤像是在门口检查：

有没有资格进场？

一条帖子即使“考试分数”很高，没有入场资格也不能出现。

这类分离很重要。

如果安全判断完全交给一个神经网络，出了问题以后，工程师很难快速回答：

> 模型为什么放行了这条内容？

独立的规则系统则更容易定位：

\`\`\`
命中了哪条规则？
规则是否被执行？
规则在排序前还是排序后生效？
\`\`\`

这次 commit 对 \`visibility-filtering\` 的规则组织进行了较大调整，使用更清晰的 \`RuleSpec\` 结构描述规则。它提升了代码的可读性和维护性，但从性质上看，更多属于安全规则工程，而非推荐模型本身的突破。

---

# 第六关：系统还要防止“作者刷屏”

假设你喜欢某个作者。

排序系统可能发现，这个作者的五条帖子分数都很高。

如果完全按分数排序，结果可能变成：

\`\`\`
作者 A
作者 A
作者 A
作者 A
作者 A
\`\`\`

这会带来一个问题：

> 你确实喜欢作者 A，但可能不想连续看五条作者 A 的内容。

所以系统会加入多样性控制。

常见做法包括：

- 同一作者连续出现时降低后续内容分数；

- 控制关注作者与未关注作者的比例；

- 让不同话题穿插出现；

- 混合图片、视频和文字；

- 给新作者一定的曝光机会。

一个简化例子：

\`\`\`
作者 A 第 1 条：0.90
作者 A 第 2 条：0.88 → 调整为 0.73
作者 A 第 3 条：0.86 → 调整为 0.62
\`\`\`

后两条并不一定质量更差。

系统只是把“最近已经出现过同一作者”也算进去了。

这里存在一个长期矛盾：

\`\`\`
只推你已经喜欢的内容
→ 信息流稳定，但越来越单一
加入更多陌生内容
→ 信息流丰富，但可能降低即时满意度
\`\`\`

推荐系统需要同时做两件事：

\`\`\`
利用：
继续推送你大概率喜欢的内容
探索：
给你一些还没有验证过的内容
\`\`\`

X 的公开代码中能看到新作者加成、站内外内容控制和作者多样性处理。不过，仅凭这些模块，不能把它直接称为完整的强化学习或 Bandit 系统。

# 第七关：\`recon\` 到底在重建什么？

这是这次 commit 中最技术的部分。

先从 embedding 说起。

模型不能直接理解：

\`\`\`
作者 ID = 928371
帖子 ID = 48291023
\`\`\`

这些数字本身没有多少语义。

系统需要把它们变成向量：

\`\`\`
作者 928371
→ \[0.12, -0.44, 0.83, 0.17, ...\]
\`\`\`

这个向量可以被神经网络继续处理。

向量中的每个数字通常没有单独、明确的人类含义，但整体结构可能反映：

- 内容主题；

- 作者风格；

- 用户兴趣；

- 社交关系；

- 历史互动模式。

---

## 传统方式：准备一张巨大向量表

最直观的方案像查字典：

\`\`\`
ID 1        → 向量 1
ID 2        → 向量 2
ID 3        → 向量 3
...
ID 100000000 → 向量 100000000
\`\`\`

大型平台的问题是，ID 数量非常大。

如果每个作者、帖子或内容对象都对应一行向量，表会变得很庞大：

- 占用内存；

- 占用存储；

- 训练时需要更新；

- 推理服务需要加载；

- 不同服务之间需要同步；

- 新对象不断加入；

- 模型导出时需要把它一起打包。

---

## \`recon\`：保存编码，需要时重建向量

\`recon\` 可以理解为 reconstruction，也就是“重建”。

它的思路类似压缩图片。

存储一张图片时，可以选择：

> 保存完整原图

也可以选择：

\`\`\`
保存压缩编码
需要使用时，通过解码器恢复
\`\`\`

在推荐系统里，大致变成：

\`\`\`
SID 编码
↓
查找离散代码
↓
decoder 重建表示
↓
投影层转换
↓
得到模型需要的 embedding
\`\`\`

于是，模型获得向量的方式变成：

\`\`\`
SID → 重建 embedding
\`\`\`

而不只是：

\`\`\`
ID → 直接查 embedding 表
\`\`\`

这意味着系统开始尝试利用一种更加紧凑、可重建的内容表示。

理论上，它可能带来：

- 更小的存储压力；

- 更低的 embedding 表依赖；

- 更容易导出模型；

- 更方便在不同服务间部署；

- 更适合固定化的推理 bundle。

不过这里需要留一个边界。

公开 commit 能确认：

- 新增了 \`sid\_embedding\_mode='recon'\`；

- 需要配套的 decoder；

- 增加了相关模型和导出逻辑。

但公开资料没有给出完整实验，因此还不能确认：

- 内存到底节省了多少；

- 推理速度到底提升还是下降；

- 推荐质量是否提升；

- 这条路径是否已经全面上线。

这部分的准确说法是：

> 代码层面是一个明确的新路径，效果层面仍缺少公开数据。

# 第八关：为什么要导出 StableHLO？

训练时，模型通常运行在灵活的 Python 环境里。

线上推理则完全是另一套要求：

\`\`\`
更低延迟
更高吞吐
更少内存
更稳定的输入形状
更容易利用硬件
\`\`\`

StableHLO 可以理解为一种模型中间表示。

它把训练阶段的模型转换成更适合编译和部署的形式：

\`\`\`
Python / PyTorch 模型
↓
StableHLO
↓
编译器优化
↓
线上推理服务
\`\`\`

为什么要关心 batch size 和 sequence length？

因为线上模型通常希望输入形状稳定。

例如系统提前准备：

\`\`\`
batch = 32
batch = 64
batch = 128

\`\`\`

请求到来时，根据候选数量选择合适规格。

这样编译器可以提前优化计算。

代价是，模型部署会更讲究版本匹配：

\`\`\`
模型版本
decoder 版本
checkpoint 版本
StableHLO bundle 版本
线上服务版本
\`\`\`

其中任何一个不匹配，都可能造成加载失败或结果异常。

所以这部分代码体现出的重点是：

> X 正在把推荐模型当作一件需要稳定交付的生产软件，而不只是一个训练完成的神经网络。

---

# 第九关：为什么要减少 query vector 的复制？

这次 commit 还优化了 \`search\_query\_embedding\` 的处理。

假设用户的搜索词已经被编码成一个向量：

> q = \[0.2, 0.5, -0.1, ...\]

现在有 100 条候选帖子。

一种做法是先复制 100 份：

> \[q, q, q, q, ..., q\]

每条候选配一份相同的查询向量。

候选数量一多，这种复制就会占用额外内存。

新的方式更接近：

\`\`\`
只保留一份 q
候选数量在推理阶段处理

\`\`\`

代码中新增的：

\`\`\`
repeat\_query\_into
num\_real\_candidates
\`\`\`

就是在处理这一类形状和候选数量问题。

还要区分两种候选：

\`\`\`
真实候选：真正来自召回系统的帖子
padding 候选：为了补齐 batch 而加入的占位数据
\`\`\`

例如：

\`\`\`
真实候选：80 条
batch 容量：128 条
\`\`\`

剩下 48 条只是占位，不能参与最终推荐。

这类细节在模型论文里经常一笔带过，在大型线上服务中却很关键。候选数、batch、padding、内存复制，都会直接影响延迟和成本。

# 这套系统是强化学习吗？

从这次公开代码来看，它更接近：

\`\`\`
多目标监督学习
+
规则过滤
+
综合排序
\`\`\`

训练时，系统根据历史行为学习：

\`\`\`
什么样的用户
看到什么样的帖子
更可能产生什么行为

\`\`\`

线上则根据模型预测结果完成排序。

典型过程是：

\`\`\`
历史行为
↓
训练多个行为预测任务
↓
预测点赞、回复、停留、负反馈等
↓
加权得到排序分数
↓
观察真实反馈
↓
继续训练和调整
\`\`\`

强化学习更强调长期决策：

\`\`\`
现在给用户看什么？
用户接下来会怎样？
长期留存和满意度如何变化？
下一步应该探索什么？
\`\`\`

仅从这次 commit，无法确认 X 是否已经把 For You 设计成完整的强化学习系统。

> 公开代码明确展示了多动作预测和多目标排序，但没有展示一套完整的端到端策略学习方案。

# 这次开源真正展示了什么？

它展示了大型推荐系统的真实结构。

推荐模型只是中间的一环。

完整系统至少包括：

\`\`\`
召回系统
用户行为建模
内容和作者表示
多动作预测
综合排序
作者多样性
安全过滤
可见性规则
模型导出
推理优化
数据管道
实验平台
\`\`\`

任何一个环节出了问题，最终的信息流都可能变差。

例如：

\`\`\`
召回不够好
→ 好内容根本进不了候选集
排序权重不合理
→ 标题党可能排到前面
负反馈处理太慢
→ 用户持续看到不喜欢的内容
多样性控制不足
→ 同一个作者刷屏
过滤规则有漏洞
→ 不该出现的内容进入信息流
模型部署低效
→ 延迟上升，系统成本增加
\`\`\`

所以，真正决定推荐质量的，往往是整条链路的配合。

# 最后的评价：亮点在哪里，疑问又在哪里？

## 亮点

1\. 多动作预测

系统同时估计点赞、回复、转发、停留和负反馈，信息比单一点击率丰富得多。

2\. 排序与安全分工

神经网络负责预测偏好，规则系统负责处理明确的安全和可见性边界。

3\. 多样性控制

系统会考虑作者重复、站内外内容比例和新作者曝光，避免信息流完全被单一来源占据。

4\. 重建式 embedding

\`recon\` 路径试图减少对巨大 embedding 表的依赖，可能改善模型表示和部署方式。

5\. 生产化程度较高

StableHLO、checkpoint 加密、buffer 复用和固定 batch 处理，说明代码关注实际线上运行，而不仅是模型训练效果。

## 仍然未知的地方

公开代码没有完整回答：

- 训练数据有多大；

- 正负样本如何构造；

- 各行为权重如何确定；

- \`recon\` 和旧方案相比提升多少；

- 线上延迟发生了什么变化；

- A/B 测试结果如何；

- 这次 commit 是否已经全面部署；

- 哪些规则和模型仍属于内部系统。

因此，目前最准确的评价是：

> 说白了，这次更新主要是在修整 X 现有的推荐流水线。最值得看的改动是 recon：SID 对应的 embedding 可以通过 decoder 重建，不再只靠原来的查表方式。周边的模型导出、批量推理、内容过滤和内存处理也一起做了调整。代码能说明“实现方式变了”，却还不能说明“推荐效果变好了”，因为官方没有公布指标、A/B 结果和性能对比。

如果只记住整篇文章的主线，可以记这段：

\`\`\`
先从全站找出可能相关的内容；
再根据用户最近的行为理解“现在的兴趣”；
然后预测用户对每条内容可能点赞、回复、停留还是反感；
把这些预测合成排序分数；
处理作者刷屏和内容多样性；
最后用独立规则守住安全边界；
同时把模型压缩、导出并优化到能承受线上流量。
\`\`\`
